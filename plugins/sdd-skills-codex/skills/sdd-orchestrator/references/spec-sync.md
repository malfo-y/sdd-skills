# spec 반영 규약

`sdd-orchestrator`의 spec 반영 단계에서 읽는다. 구현 전(planned)과 구현 후(implemented) 반영을 같은 규약으로 처리한다. 원칙은 하나다. 일회성 실행 정보는 버리고, 저장소 전체에 오래 남을 정보만 가장 맞는 자리에 보수적으로 반영한다.

## 입력

구현 후일수록 위쪽을 우선한다.

1. 실제 코드 변경과 그 검사 결과
2. 계획 파일의 마커 구간(`spec-update-todo-input`)과 `진행` 절(조건별 판정과 증거)
3. 대화에서 나온 사용자 결정
4. `_sdd/spec/user_spec.md`, `_sdd/spec/user_draft.md`
5. `_sdd/spec/decision_log.md`

예전 산출물도 입력으로 받는다: `_sdd/implementation/` 아래 state·plan·progress·review·report 파일, 대문자 `DECISION_LOG.md`, 예전 형식 계획 파일의 Part 1 마커 구간과 task별 `Contracts`·AC.

## 항목별 분류

반영할 항목마다 실제 코드와 검증 증거를 기준으로 넷 중 하나로 분류한다. 증거가 없으면 PLANNED가 기본이다.

- **IMPLEMENTED**: 코드와 증거가 있다. 표식 없이 현재 사실로 쓴다.
- **PARTIAL**: 구현되고 검증된 부분은 현재 사실로 쓰고, 남은 부분은 `🚧 Planned`로 나눈다.
- **PLANNED**: 증거가 없다. `🚧 Planned` 표식을 붙여 쓴다(`## 🚧 Planned ...`, `- 🚧 Planned: ...`).
- **UNVERIFIED**: 코드는 있으나 계획의 조건·증거와 연결되지 않는다. 반영을 보류하고 `Open Questions`에 남긴다.

검증된 현재 사실과 planned 내용을 같은 문단이나 불릿에 표식 없이 섞지 않는다. 계획 파일에 나눈 기능 목록이 있으면 기능 하나당 `🚧 Planned` 항목 하나로 쓴다. 이후 그 기능이 구현되면 해당 항목만 승격하거나 지운다.

## 어디에 쓰는가

먼저 정보가 `main.md`, 보조 문서, 기록(decision log), 또는 계획 파일 중 어디에 남아야 하는지 정하고, 가장 맞는 한 곳에만 쓴다.

- 문제 정의나 접근의 변화 → `배경 및 high-level concept`
- 범위·비목표·저장소 운영 규칙의 변화 → `Scope / Non-goals / Guardrails`
- 오래 유지할 설계 판단의 변화 → `핵심 설계와 주요 결정`
- 반복해서 쓰일 진입점·확장 지점·검증 지점 → `Strategic Code Map` 또는 보조 문서

저장소 전체 불변 규칙은 아래 셋을 모두 만족할 때만 Guardrails나 주요 결정에 쓴다.

1. 코드 한두 파일을 읽어서는 안정적으로 알아낼 수 없다.
2. 둘 이상의 기능·모듈·작업 흐름에 공통으로 적용된다.
3. 틀리게 가정하면 저장소 수준의 판단·리뷰·구현이 어긋난다.

global spec에 올리지 않는 것: 기능 하나의 계약 표, 검증 실행 상세, 작업 분해, 바꾼 파일 목록, 일시적 위험 기록, 사용법 안내, 전체 파일 목록.

구조 규칙:

- 새 보조 spec 파일을 만들면 `main.md` 인덱스에 링크를 넣는다.
- 기존 파일의 분할 구조는 바꾸지 않는다. 파일 추가만 한다.
- 코드와 구현 문서는 이 단계에서 고치지 않는다.
- 서로 충돌하거나 불명확한 요구는 비파괴적인 쪽만 반영하고 `Open Questions`에 남긴다.

## 쓰는 순서

1. **현재 사실**: 고른 `_sdd/spec/` 파일을 고친다. 분류대로 쓰고, 낡은 서술은 지운다. 기존 문체와 언어를 맞추고 같은 사실을 두 곳에 쓰지 않는다. `main.md`의 헤더 밖 본문이 바뀌면 헤더의 `Spec Version`을 SemVer로 올린다.
2. **기록**: 기존 entry는 고치거나 지우지 않고 새 entry만 덧붙인다.
   - `decision_log.md`: 결정의 근거가 바뀌었을 때만 최소 entry.
   - `logs/changelog.md`: `main.md` 본문이 바뀐 버전마다 entry. 버전은 헤더와 같아야 한다.
3. **입력 파일**: 반영을 마친 일회성 제출물(`user_spec.md`, `user_draft.md`)과, 모든 조건이 닫히고 남은 분할 기능이 없는 계획 파일은 `_processed_` 접두로 rename한다. 내용은 보존한다. 이미 접두가 있거나 목적지 파일이 있으면 rename하지 않고 사유를 보고한다.
4. **환경 함정**: 이번 작업에서 확인한 환경 사실 중 이 기능을 넘어 저장소 작업에 반복 적용되는 것을 `_sdd/env.md`의 가장 맞는 절에 쓴다.
   - 이미 있는 사실은 다시 쓰지 않고, 어긋나는 기존 항목은 고친다.
   - 커밋되는 파일이다. 비밀값을 적지 않는다. 셸·OS·도구 버전에 따라 달라지는 사실은 조건과 함께 쓴다.
   - 기능별 결정, 검증 명령, 임시 경로, 파일별 수치는 올리지 않는다.
   - 파일이 없으면 상단에 비밀값 금지 경고를 두고 만든다.

## 끝내기 전 확인

- 증거 없는 내용이 완료된 것처럼 남지 않았는가.
- global spec이 기능 수준 상세로 두꺼워지지 않았는가.
- 경로와 참조가 현재 코드와 맞는가.
- `main.md` 본문을 고쳤다면 헤더 버전과 `logs/changelog.md` 최신 entry 버전이 같은가.
- 기록 파일에서 이번 실행이 기존 entry를 고치거나 지우지 않았는가. 시작 전부터 있던 미커밋 변경은 이번 위반으로 보지 않고 따로 보고한다.
