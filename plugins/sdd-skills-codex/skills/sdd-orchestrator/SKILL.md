# SDD Orchestrator

요청 하나를 계획에서 spec 반영까지 메인 세션이 직접 끝낸다. 이 스킬이 정하는 것은 단계 순서와, 모델이 추론할 수 없는 저장소 규약뿐이다. 각 단계를 어떻게, 얼마나 깊이 할지는 작업의 크기와 위험에 맞게 스스로 정한다. 단계 작업(계획·리뷰·구현·spec 반영)은 다른 agent에 넘기지 않는다. 넘기면 받는 쪽이 같은 코드를 처음부터 다시 읽는 시간이 든다.

## Goal

요청이나 계획 파일을 받아 정한 종점까지 아래 단계를 순서대로 직접 수행하고, 끝나는 조건마다 증거가 묶인 상태로 마감한다.

## Acceptance Criteria

> 종료 전 `Final Check`대로 점검한다.

- [ ] AC1: 시작 단계와 종점을 `단계와 진입`으로 정했고, 그 범위의 단계를 순서대로 수행했다.
- [ ] AC2: 계획 파일이 `계획 파일` 절의 경로와 구조를 따르고, 끝나는 조건마다 판정 방법이 있다.
- [ ] AC3: 충족으로 적은 조건마다 이번 실행에서 얻은 증거(실행 출력 또는 `file:line`)가 있다. 증거가 없는 조건은 충족으로 적지 않았다.
- [ ] AC4: 마감 보고에 실행으로 확인하지 못한 것과 사용자 결정이 필요했던 지점이 있다.

## 단계

1. **계획**: 요청과 대화에서 나온 결정을 읽고, 코드·spec·`_sdd/env.md`를 필요한 만큼 살펴 `계획 파일`을 쓴다.
   - 끝나는 조건은 제3자가 실행 출력이나 인용 근거로 충족 여부를 가를 수 있게 쓴다.
   - 요청에서 직접 나오지 않는 기능·추상화·새 파일은 계획하지 않는다.
   - 바꿀 자리와 끝나는 조건의 대응을 한눈에 검산할 수 없을 만큼 크면 기능 단위로 나눈다. 나눈 기능 목록을 계획 파일의 Spec Delta에 적고, 첫 기능만 종점까지 진행한 뒤 멈춘다.
   - 이름 변경이나 전파처럼 같은 대상의 여러 표기가 여러 파일에 흩어진 변경은, 변형 표기(kebab·underscore·공백·경로)까지 전수 검색한 잔존 0건을 끝나는 조건으로 둔다. 단일 패턴 검색은 잔존을 반복해서 놓쳤다.
2. **계획 리뷰**: 코드를 고치기 전에 계획을 한 번 검토한다. 계획이 기대는 외부 사실(파일·함수·시그니처·호출처·경로·문서 규칙·실행 환경)을 실제와 대조한다. 계획이 바꾸는 값이나 약속을 읽는 다른 자리를 검색해 빠진 수정 지점을 찾는다. 끝나는 조건마다, 통과해도 결함이 남을 수 있는지 본다. 찾은 것은 계획 파일에 반영한다.
3. **구현**: 끝나는 조건마다 실패하는 검사를 먼저 만들어 실패를 확인한 뒤, 통과시키는 가장 작은 변경을 한다.
   - 검사는 테스트이거나, 테스트 프레임워크가 없는 자산이면 검색·diff·종료 코드로 판정하는 검사다. "파일이 있다" 수준이라 판정 가치가 없는 검사는 만들지 않는다.
   - 검사의 종류와 강도(일부러 틀리게 바꿔 검사가 잡는지 보는 확인 등)는 위험에 맞게 정한다.
   - 검사를 통과시키려고 검사를 약하게 고치지 않는다. 검사의 전제가 틀렸으면 무엇이 왜 틀렸는지 계획 파일에 적고 고친다.
   - 계획과 달라진 결정은 계획 파일의 `진행`에 적는다.
4. **구현 리뷰**: 검사가 통과하면 전체 diff를 처음부터 다시 읽는다. 검사 통과는 검사가 닿는 동작만 증명하므로 닿지 않는 곳을 본다. 요구사항 중 구현되지 않은 것, 검사가 통과해도 틀리게 동작할 수 있는 곳, 이 환경에서 실행해 보지 못한 조건(다른 장비·규모·동시 실행), 요청에 없는 코드와 중복이 대상이다. 찾은 것은 바로 고치고 관련 검사를 다시 돌린다.
5. **spec 반영**: `references/spec-sync.md`를 읽고 그 규약대로 `_sdd/spec/`과 `_sdd/env.md`를 고친다.
6. **마감**: 계획 파일의 `진행`에 조건별 판정과 증거를 적고 채팅에 보고한다. 보고에는 수행한 단계, 조건별 결과, 두 리뷰에서 찾아 고친 것, 실행으로 확인하지 못한 것, 사용자 결정이 필요했던 지점과 고른 안, 남은 분할 기능을 담는다. 상위 하네스에 work log 규약이 있으면 그 규약대로 기록한다.

## 사용자 결정

- 답에 따라 구조·범위·바꿀 자리가 달라지는 것만 묻는다. 한 번에 하나씩 묻고, 이미 승인된 결정과 일상적인 선택은 다시 묻지 않는다.
- 사용자가 무인 실행을 맡겼으면 묻지 않고 가장 합당한 안으로 진행하며, 그 지점과 고른 안을 마감 보고에 적는다.
- commit·push 같은 git 쓰기는 사용자가 요청했거나 미리 승인했을 때만 한다.

## 계획 파일

경로는 `_sdd/drafts/<YYYY-MM-DD>_feature_draft_<slug>.md`이고 `slug`는 소문자 snake_case다. 아래 구조에서 마커 쌍과 세 절의 제목만 고정이다. 절 안의 형식과 분량은 작업에 맞게 정한다.

```markdown
# [제목]

<!-- spec-update-todo-input-start -->
## Spec Delta
[무엇이 왜 바뀌는가. 다른 코드·문서·이후 작업이 새로 의지하게 될 약속. 범위 In / Out. 기능을 나눴으면 남은 기능 목록(기능당 1줄).]
<!-- spec-update-todo-input-end -->

## 계획
[바꿀 자리. 끝나는 조건과 조건마다의 판정 방법. 계획이 기대는 외부 사실.]

## 진행
[현재 단계. 조건별 판정과 증거. 계획과 달라진 결정. 실행으로 확인하지 못한 것.]
```

- 마커 구간은 spec 반영의 입력이다. 마커 쌍을 지우지 않는다.
- `진행`은 재개용이다. 세션이 끊기면 이 절을 읽고 이어 가며, 충족으로 적히지 않은 조건은 다시 판정한다.
- 예전 형식(`# Part 1: Spec Delta`, `# Part 2: Tasks`)의 파일도 그대로 입력으로 받는다.

## 단계와 진입

- 요청만 있으면 계획부터 시작한다.
- 계획 파일이 있으면 그 `진행`이 가리키는 곳부터 시작한다. 진행 기록이 없으면 계획 리뷰부터 시작한다.
- 기본 종점은 spec 반영이다. 사용자가 종점이나 단계를 지정하면 그대로 따른다.
- discussion은 이 스킬 밖이다. discussion 요약 파일은 입력으로만 쓴다.

### 호출 이름

예전 단계 스킬 이름으로 호출되면 아래 범위만 수행한다.

| 호출 이름 | 범위 |
|-----------|------|
| feature-draft | 계획과 계획 리뷰까지 하고 멈춘다. |
| plan-review | 계획 리뷰만 한다. 찾은 것을 보고하고 계획 파일은 고치지 않는다. 대상은 지정한 경로이고, 없으면 `_sdd/drafts/`에서 `_processed_` 접두가 없는 최신 계획 파일이다. |
| implementation | 계획 파일이 있으면 구현부터, 없으면 계획부터 시작한다. 구현 리뷰까지 하고 멈춘다. |
| implementation-review | 구현 리뷰만 한다. 찾은 것을 보고하고 고치지 않는다. 기준은 지정한 계획 파일이고, 없으면 이번 변경과 관련된 최신 계획 파일, 그것도 없으면 spec과 diff다. |
| spec-sync | spec 반영만 한다. |

## Final Check

수행한 범위에 해당하는 Acceptance Criteria를 한 번 점검한다. 보완할 수 있는 누락은 고친다. 외부 사정으로 막힌 것은 미충족 조건·사유·다음 조치로 보고하며, 충족으로 표시하지 않는다.
