# Guide Create Output Format

`guide-create`가 쓰기 직전에 읽는다. 기능 기술 보고서의 파일 규칙, 구조, 절별로 꼭 들어갈 내용을 정한다.

## 1. 파일 규칙

- 경로: `_sdd/guides/<YYYY-MM-DD>_guide_<slug>.md`
- `slug`: 영문 소문자, 숫자, `_`만 쓴다. 공백·하이픈·슬래시는 `_`로 바꾼다. 50자 이하를 권장한다. 기능 이름이 한국어뿐이면 뜻을 옮긴 영문 요약을 쓴다.
- 기능이 여럿이면 기능마다 파일을 나눈다. 이름이 겹치면 slug에 더 구체적인 단어를 붙인다.

## 2. 쓰는 규칙

- §3의 fenced skeleton을 복사한다. 문서 언어에 맞춰 제목과 표시 label은 번역할 수 있지만, 계층·순서·metadata 필드의 뜻·필수 5개 절은 유지한다. 그 밖에는 자리 표시만 근거 있는 내용으로 바꾼다.
- 본문 주장에는 `[filepath:symbolName]` 형식의 citation을 붙인다.
- 코드 발췌는 첫 줄에 `# [filepath:functionName]`을 두고, 주장을 증명하는 최소 범위만 싣는다.
- 부록은 관련 근거가 있을 때만 둔다.

## 3. 문서 필수 구조

```markdown
# 기능 기술 보고서: <feature name>

**Version**: X.Y.Z
**Status**: Draft | In Review | Approved | Deprecated
**생성일**: YYYY-MM-DD
**입력 소스**: conversation / spec / code / mixed
**대상 기능**: <feature name>
**신뢰도**: High / Medium / Low

## §1 배경 및 동기
[이 기능이 해결하는 문제, 왜 필요한가, 대안 대비 선택 이유]

## §2 핵심 설계
[핵심 아이디어/알고리즘, 설계 결정과 이유, 코드 citation]

## §3 사용 시나리오 가이드
[시나리오별 end-to-end 사용 흐름, 정상/예외 시나리오]

## §4 API 레퍼런스
[인터페이스 상세, 파라미터, 리턴값, 에러, 코드 예시]

## §5 구현 가이드
[핵심 규칙, 체크리스트, 안티패턴]
```

## 4. 절별로 꼭 들어갈 내용

- **§1 배경 및 동기**: 해결하는 문제, 필요한 이유, 대안 대비 선택 이유(spec에서 확인될 때). spec에 배경이 없어 문맥에서 추론했으면 가정이라고 적는다.
- **§2 핵심 설계**: 동작 원리, 주요 설계 결정과 이유, 그것을 보여 주는 citation과 코드 발췌. 코드 근거가 없으면 spec 기준으로 쓰고 "코드 미확인"이라고 적는다.
- **§3 사용 시나리오 가이드**: 이 문서의 중심이다. 근거가 있는 대표 end-to-end 흐름마다 전제 조건, 입력, citation이 붙은 처리 흐름, 기대 결과를 잇는다. 확인된 예외·에러 근거가 없으면 시나리오를 만들지 않고 `확인된 예외/에러 시나리오 없음`과 근거의 한계를 적는다.
- **§4 API 레퍼런스**: 인터페이스(endpoint·함수·타입)마다 시그니처, 구현 위치 citation, 파라미터 표(이름 | 타입 | 필수/선택 | 설명), 리턴값·응답, 에러, 호출 예시. 외부 API가 없는 기능이면 그렇게 적고 내부 인터페이스를 같은 구조로 쓴다.
- **§5 구현 가이드**: 핵심 규칙(상태 변화·에러 처리·데이터 검증과 저장, 코드 근거가 있으면 citation), 체크리스트(구현 전 / 구현 중 / 완료·리뷰 전, 항목마다 검증할 수 있는 문장), 안티패턴과 그 근거. 근거가 약한 규칙은 "권장"·"추정"·"가정"이라고 적는다.

## 5. 부록

- **관련 스펙 레퍼런스**: 파일 경로와 절 이름을 함께 적는다. 예: `_sdd/spec/main.md` → `목표 > 결제 승인`
- **관련 코드 레퍼런스**: 파일 경로와 심볼 이름을 함께 적는다. 예: `src/payments/service.ts` - `confirmPayment`
- **가정 및 미확정 사항**: 근거가 부족한 부분을 숨기지 않고 적는다.

## 6. 신뢰도

- **High**: 배경·설계·시나리오·API가 spec과 코드 모두에서 확인된다.
- **Medium**: 배경과 설계는 spec에서 확인되지만 시나리오나 API 세부의 일부가 추론이다.
- **Low**: spec 근거가 약하거나 코드 근거가 거의 없어 가정의 비중이 크다.
