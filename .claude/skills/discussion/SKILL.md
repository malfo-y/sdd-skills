# Structured Discussion - 구조화된 토론 진행

| Workflow | Position | When |
|----------|----------|------|
| Any | Standalone | 기술적 주제에 대한 구조화된 토론 |
| Any | Pre-draft | 방향/요구사항 불명확 시 논의 후 feature-draft 연계 |

구조화된 반복 토론을 진행한다. 프로빙 질문으로 주제를 심층 탐구하고, sub-agent를 활용해 코드베이스 탐색 및 웹 리서치를 수행하며, 토론 종료 시 구조화된 요약을 저장한다.

## Acceptance Criteria
> 정상 완료 기준이다. 중단·미완료 저장과 복구 범위는 Error Handling·Final Check를 따른다.
- [ ] AC1: 구조화된 토론이 최소 1라운드 이상 진행되었다
- [ ] AC2: key decisions / action items가 내부 상태에 추적·정리되었다
- [ ] AC3: 토론 요약 파일이 `_sdd/discussion/<YYYY-MM-DD>_discussion_<slug>.md`에 저장되었다
- [ ] AC4: 요약에 토론 배경/초기 콘텍스트, 핵심 논점, 결정 사항, 미결 질문, 실행 항목 섹션이 모두 포함되었다

## Hard Rules

1. **토론은 read-only다**: 코드·스펙·설정을 수정하지 않는다(`Edit`·mutation `Bash` 금지). 파일 쓰기는 Step 4의 요약 파일 저장(`Write` + `mkdir -p _sdd/discussion/`)이 유일한 산출 경로다. 단, 호출 환경의 work log 규약에 따른 작업 기록 append는 이 제한의 예외다.
2. **토론 종료 옵션 항상 포함**: Step 3의 매 질문에 정리/종료 성격의 선택지를 포함한다.
3. **AskUserQuestion 도구 필수**: Step 3 토론 루프에서 사용자에게 질문할 때 반드시 `AskUserQuestion` 도구를 사용한다.
4. **in-scope 미결 종료 차단**: 카테고리가 `out-of-scope`나 `deferred-deliberately`가 아닌 미결(이하 "in-scope `open_questions`")이 남은 상태로는 Gate 3→4 외 어떤 경로(수렴 신호, stagnation fallback 등)로도 정상 종료하지 않는다. 사용자 중단·응답 단절 시 부분 저장은 Error Handling을 따른다.

## Key Principles

Process의 모든 단계에서 횡단 적용되는 원칙. Hard Rules가 강제 금지라면, Key Principles는 판단 지침이다.

- **One question at a time**: 한 라운드에 여러 질문을 묶지 않는다. 한 주제가 깊이를 요구하면 여러 라운드로 쪼갠다.
- **Multiple choice preferred**: 가능하면 MC 형식이 우선. 자유 서술은 사용자가 카테고리로 압축 불가능할 때만 사용.
- **YAGNI ruthlessly**: 요구사항/범위가 부풀 때 적극적으로 쳐낸다. "지금 필요한가?"를 비판적 개입(3.2.2)의 기본 질문으로 삼는다.
- **Explore alternatives (2-3안 + 권장안)**: Analysis 페이즈에서 AI가 능동적으로 2-3개 구별되는 접근을 제시하고 권장안을 먼저 말한다. 상세는 Step 3.2.1 참조.
- **Incremental validation**: 수렴은 한 번에 이뤄지지 않는다. 논의가 쌓이면(3.4) 중간 요약으로 이해도를 확인하고, 수렴 신호(3.5)가 감지되면 종료를 권유.
- **Be flexible**: 새 정보가 기존 결론을 흔들면 페이즈를 되돌린다. 깊이 신호(3.2) 감지 시 phase 무시.
- **Respect existing patterns, contain scope**: 토론에서 제안되는 변경안은 기존 코드베이스/문서 패턴을 먼저 이해하고 따라야 한다. 작업과 관련된 개선은 토론에 포함하되, 관련 없는 리팩터링/확장 제안은 배제. 범위 드리프트를 감지하면 원래 토픽으로 리마인드.

## Process

### Step 1: Topic Selection (토픽 선택)

**Tools**: `AskUserQuestion`

입력만으로 아래 Gate를 충족하면 범위를 한 문장으로 재진술하고 Step 2로 진행한다. 빠진 범위 결정이 있을 때만 그 한 가지를 질문한다.

- 토픽이 불명확하면 코드베이스·아키텍처·기술 선택 등의 예시로 질문을 좁힌다. 자유 입력도 수용한다.
- **Scope atomicity 점검**: 독립적 서브시스템 묶음(예: 인증 + 결제 + 알림)이면 분해와 순서를 제안하고, 사용자와 첫 번째 서브프로젝트를 선택한다. 단일 단위면 추가 분해하지 않는다.

**Decision Gate 1→2**: `topic_defined AND scope_clear AND scope_is_atomic` → Step 2 진행. ELSE → AskUserQuestion으로 보완 (최대 2라운드). 다중 서브시스템이면 분해 후 단일 서브프로젝트로 좁힌 뒤 게이트 재평가.

### Step 2: Context Gathering (맥락 수집)

**Tools**: `Agent` (Explore, general-purpose), `Read`, `Glob`, `Grep`

토픽에 따라 자동으로 관련 자료를 수집한다.

#### 2.1 토픽 유형별 자동 리서치

| 토픽 유형 | 자동 액션 | Sub-agent 유형 |
|-----------|----------|----------------|
| 코드베이스 관련 | 코드베이스 구조/패턴/관련 파일 탐색 | Explore |
| 아키텍처 설계 | 현재 아키텍처 파악 + 관련 패턴 리서치 | Explore + general-purpose (병렬) |
| 기술 선택 | 후보 기술 비교 자료 수집 | general-purpose |
| Other | 사용자 입력 기반 판단 | 필요시 Explore 또는 general-purpose |

#### 2.2 맥락 요약

수집된 정보를 사용자에게 간략히 보고:
```
## 수집된 맥락
| 항목 | 내용 |
|------|------|
| 관련 파일 | N개 식별 |
| 주요 패턴 | ... |
| 외부 참고 | ... (있는 경우) |
```

#### 2.3 Initial Context Capture (필수)

Step 2에서 수집한 맥락은 사용자에게 보여주는 일회성 요약으로 끝내지 않고, 최종 요약에 재사용할 수 있도록 `initial_context` 내부 상태에 보존한다.

`initial_context`에는 아래를 간결하게 기록한다:

- **사용자 문제 제기**: 사용자가 처음 어떤 필요/불편/질문으로 토론을 시작했는지
- **토론을 시작한 배경**: 왜 지금 이 토론이 필요한지, 어떤 후속 작업이나 의사결정과 연결되는지
- **현재 상태**: 코드베이스/문서/운영 상황 등 확인된 현황
- **범위와 제외 범위**: 이번 토론에서 다루기로 한 것과 명시적으로 미룬 것
- **수집한 근거**: 로컬 파일, 문서, 외부 자료 등 토론 전제에 영향을 준 자료

이 항목은 결정이나 논점과 중복되더라도 삭제하지 않는다. 목적은 "무엇을 결정했는가"가 아니라 "왜 이 토론이 열렸는가"를 후속 독자가 복원할 수 있게 하는 것이다.

**Decision Gate 2→3**: `context_available AND topic_still_valid` → Step 3 진행. 맥락 없으면 사용자에게 확인. 토픽 무효화 시 Step 1 복귀.

### Step 3: Iterative Discussion (반복 토론)

**Tools**: `AskUserQuestion`, `Agent` (Explore, general-purpose), `Read`, `Glob`, `Grep`

핵심 토론 루프. 사용자와 반복적으로 심층 질문-답변을 수행한다.

#### 3.1 토론 루프 구조

**내부 상태**: `key_points` · `decisions` · `open_questions` · `action_items` · `rejected_alternatives` · `conversation_log` · `initial_context` · 라운드 번호, 그리고 **coverage 맵** — exploration(`motivation`, `current_state`, `constraints`, `ideal_outcome`) / analysis(`alternatives`, `tradeoffs`, `priorities`, `critical_review`) / convergence(`conclusion`, `risks`, `action_items`).

매 라운드는 다음 흐름을 반복한다: 3.2 전략으로 질문을 하나 고르고, `AskUserQuestion`으로 제시하며(활성 도구 schema 안에서 정리/종료를 포함해 총 옵션 2-4개), 응답을 분석해 내부 상태와 coverage를 갱신한다. 근거가 필요하면 리서치를 디스패치하고(3.3), 리서치·답변이 기존 결정의 전제와 모순되면 결정을 재방문하며(3.3.1), 수렴 신호가 감지되면 종료를 권유한다(3.5). 사용자가 "토론 종료"를 선택하거나 "정리해줘"를 입력하면 Gate 3→4로 이동한다.

**근거 유형 기록 (필수)**: `decisions`에 항목을 추가할 때 근거와 함께 **근거 유형**을 기록한다 — `코드 확인`(파일/코드를 직접 확인한 사실) / `외부 자료`(리서치로 수집한 자료) / `사용자 판단`(사용자의 의도·선호 결정) / `미검증 가정`(검증 없이 전제한 사항) 4종 고정. 자기 확신을 근거로 위장하지 않는다 — 확인하지 않았으면 `미검증 가정`으로 표기한다.

#### 3.2 질문 선택 전략 (커버리지 기반 하이브리드)

라운드 번호가 아닌 **커버리지 달성도**가 페이즈를 결정한다. 매 라운드, 직전 답변에 깊이 신호가 있으면 페이즈를 무시하고 그 지점을 파고드는 후속 질문을 우선한다. 깊이 신호가 없으면 coverage 맵에서 페이즈를 판정한다 — exploration 미확인 항목이 있으면 탐색 질문, exploration이 끝났고 analysis 미확인이 있으면 분석 질문, 둘 다 끝났으면 수렴 질문.

같은 페이즈 안에서 후보 질문이 여럿이면 **답이 아키텍처를 바꾸는 질문**(구조·범위·후속 작업 방향이 달라지는 질문)을 먼저 묻는다 — 뒤늦게 답이 나오면 앞선 결정들이 무효가 되는 질문일수록 앞에 온다.

**깊이 신호** (페이즈 무시하고 파고드는 트리거): 모순 발견 · 불확실성 표현("잘 모르겠는데...") · 새 제약조건 등장 · 강한 의견(이유를 파고들기). 신호별 예시 문형은 `references/discussion-question-guide.md` 참조.

**수렴 전 안전장치:** 수렴 페이즈 진입 전 exploration/analysis에 미확인 항목이 있으면 사용자에게 "아직 [항목]을 다루지 않았는데, 넘어가도 괜찮을까요?" 확인.

#### 3.2.1 Alternatives Initiation (필수)

Analysis 페이즈 진입 직후 첫 라운드에, AI는 다음을 반드시 수행한다:

1. **2-3개의 구별되는 접근을 능동적으로 제시.** 사용자가 먼저 대안을 꺼낼 때까지 기다리지 않는다.
2. 각 접근에 대해 1-2줄 트레이드오프를 명시.
3. **권장안을 먼저 제시하고 이유를 붙인다.** 중립 나열만 하지 않는다.
4. `AskUserQuestion`의 옵션으로 각 접근을 제시하거나, 텍스트로 제시한 뒤 후속 `AskUserQuestion`으로 선택을 유도.

사용자가 특정 방향을 명시적으로 고정했다면 `alternatives = skipped (사용자 지정)`와 사유를 기록하고 바로 비판적 개입(3.2.2)으로 진행한다. 이 생략은 페이즈 판정에서 충족으로 취급하며 다시 승인받지 않는다. 요약의 범위와 제외 범위에도 사유를 남긴다.

사용자가 선택하지 않은 접근은 기각 사유와 함께 `rejected_alternatives`에 기록한다 (요약의 "기각한 대안" 섹션 입력 — 후속 작업이 같은 대안을 재검토하는 낭비를 막는다).

**커버리지 체크:** 방향이 열려 있으면 능동 제시 후 사용자 응답을 받아야 `alternatives`를 완료로 표시한다. 사용자 지정 생략을 대안 비교 완료로 기록하지 않는다.

#### 3.2.2 비판적 개입 (Critical Review)

분석 페이즈에서는 최소 1회 **비판적 질문**으로 약점이나 숨은 가정을 검증한다. 3.2.1의 대안 제시 완료 또는 사용자 지정 생략 후 수행한다.

- 사용자가 특정 방향에 합의/선호를 표현하면 그 방향에 대해 비판적 질문을 우선 제시한다.
- 사용자가 끝까지 중립 비교 상태라면, 현재 가장 가능성이 높은 방향이나 공통 가정을 임시 가설로 잡고 비판적 질문을 1회 수행한다.
- 임시 가설도 성립하지 않으면 "가장 우려되는 실패 시나리오" 또는 "지금 가정이 틀리면 무엇이 깨지는지"를 묻는 방식으로 `critical_review`를 충족한다.

**비판적 개입 유형**: 약점 지적(방향이 정해졌을 때) · 반례 제시(장점만 언급될 때) · 숨은 가정 질문(전제가 검증 안 됐을 때) · 대안 제안(탐색 범위가 좁을 때) · 스케일 도전(현재 규모만 고려할 때) · YAGNI/범위 축소(요구사항이 부풀 때). 유형별 예시 문형은 `references/discussion-question-guide.md` 참조.

**강도 조절 규칙:**

1. 비판이 연속으로 몰리지 않게 완급을 조절한다 — 비판 라운드 뒤에는 건설적 질문을 섞는다
2. 비판 후에는 대안이나 보완책을 함께 제시
3. 사용자가 이미 반박한 약점은 재차 제기하지 않음
4. 비판은 "질문" 형태로 — 단정이 아니라 탐색 유도

**커버리지 체크:** `critical_review`는 분석 페이즈에서 최소 1회 비판적 개입이 이루어지고 사용자가 응답했을 때 완료로 표시한다. 선호가 없는 비교형 토론도 fallback 비판 질문으로 완료 가능해야 한다. 비판적 검토 없이 수렴으로 넘어가는 것을 방지한다.

#### 3.2.3 Soft Deferral Handling (묵시적 떠넘김 차단)

사용자가 토론 중 묵시적 deferral 신호(예: "나중에 보죠", "그건 구현하면서", "지금은 모르겠는데", "일단 넘어가요")를 보이면, AI는 메타-분류 질문을 사용자에게 노출하지 않고 **내부적으로** 다음 분류를 수행한다.

| 분류 | 조건 | AI 처리 |
|------|------|---------|
| (a) 지금 답 가능 | 한 가지 구체 질문으로 좁히면 사용자가 토론 내에서 답할 수 있다 | 좁힌 1회 재질문(1라운드 한정, 3.2.2 비판 카운트에서 제외). 그래도 답 못 하면 (b)로 강등 |
| (b) 토론 외부 deferred | 다른 작업/외부 데이터 대기/명확한 분리가 정당함 | `open_questions`에 카테고리 `deferred-deliberately` 또는 `needs-data`로 조용히 기록 |
| (c) 다른 미결 의존 | 동일 토론 내 다른 미결 질문이 풀려야 답 가능 | `blocked-by:Q<n>` 라벨로 기록하고, 의존하는 Q를 **다음 라운드 우선 주제**로 채택 |

**규칙:**

1. 분류는 AI 내부 추론으로만. "이거 (a/b/c) 중 뭐죠?" 같은 메타 질문을 표면에 노출하지 않는다 (fatigue 방지).
2. 묵시적 deferral을 그냥 받아 `open_questions`에 in-scope로 적재하는 행위는 금지. 반드시 위 분류를 거친다.

#### 3.3 Mid-Discussion Research

토론 중 근거가 필요하면 sub-agent를 즉시 디스패치:

| 트리거 | Sub-agent |
|--------|-----------|
| "추가 리서치 필요" 선택 | general-purpose |
| 코드베이스 확인 필요 | Explore |
| 사실 확인 필요한 주장 | general-purpose |

독립적인 리서치 2건 이상이면 병렬 디스패치.

#### 3.3.1 결정 재방문 (Decision Revisit)

리서치 결과나 새 사용자 답변이 기존 `decisions` 항목의 **전제**와 모순되면, 그 결정을 낡은 전제 위에 그대로 두지 않는다:

1. 해당 결정을 **다음 라운드 주제로 자동 채택**해 재방문한다. 질문 본문에 무엇이 모순되는지 명시한다.
2. 같은 결정을 반복 재방문하며 표류하지 않는다 — 한 번 재방문해 해소되지 않은 결정은 다시 재방문 주제로 채택하지 않는다.
3. 재방문 후에도 해소되지 않으면 결정을 폐기하지 말고 `open_questions`로 강등한다 (카테고리 라벨링 대상).
4. 재방문으로 변경·강등된 결정은 요약의 결정 테이블에 변경 이력 1줄을 남긴다 (어떤 전제가 무너져 어떻게 바뀌었는지).

#### 3.4 중간 상태 추적

누적된 논의가 한눈에 안 들어올 만큼 쌓였다고 판단되면 (대략 페이즈 전환 시점, 또는 사용자 요청 시) 핵심 논점·결정 사항·미결 질문·실행 항목 카운트를 중간 요약 테이블로 제시.

#### 3.5 수렴 신호 감지 및 종료 유도

라운드 수 제한 없이, 아래 **수렴 신호**가 충분히 감지되면 종료를 권유한다.

**수렴 신호:**

| 신호 | 감지 기준 |
|------|----------|
| 반복 합의 | 사용자가 연속된 라운드에서 동의/확인 응답만 반복 |
| 새 정보 없음 | 직전 라운드에서 key_points/decisions에 추가된 항목 없음 |
| 명시적 만족 | "좋아요", "그걸로 하죠", "충분해요" 등 |
| 커버리지 충족 | exploration + analysis 항목 모두 충족(사용자 지정 생략 포함) |

**2개 이상 신호 동시 감지 시:**
```
"지금까지 [N]개 논점을 다루고 [M]개 결정을 내렸습니다.
 정리해도 좋을 것 같은데, 더 논의할 내용이 있으신가요?"
 1) "정리해줘"
 2) "[추가 논의 주제 제안]"
```

사용자가 추가 논의를 선택하면 계속 진행한다. 종료를 강제하지 않는다.

**가드**: in-scope `open_questions`이 1건 이상이면 위 수렴 신호가 충족돼도 종료 권유 메시지를 발화하지 않는다. 대신 해당 미결을 다음 라운드 주제로 자동 채택한다 (`blocked-by:Q<n>` 의존이 있으면 의존하는 Q를 우선).

#### 3.5.1 Stagnation Fallback

토론이 길어지더라도 **단순 라운드 수로 종료하지 않는다**. 대신 아래 정체(stagnation) 신호를 본다.

**stagnation 신호:**

| 신호 | 감지 기준 |
|------|----------|
| 새 정보 없음 | 연속 라운드에서 `key_points`나 `decisions`가 늘지 않음 |
| 미결 질문 정체 | 같은 open question이 재진술되지만 진전이 없음 |
| 반복 유보 | 사용자가 연속적으로 모호한 답변, 유보, "더 봐야 할 것 같아요" 류 응답을 함 |

**stagnation 대응 규칙:**

1. stagnation 신호가 해소되지 않고 거듭 감지되면 질문 범위를 강제로 좁힌다.
2. "남은 미결 1개만 더 논의"와 "정리/종료"를 제시한다. 종료 선택은 Gate 3→4로 이동한다. 대상 질문의 짧은 요약을 질문 본문이나 옵션에 함께 보여준다. 미결이 없으면 실제 추가 논점을 제안하고, 없는 미결을 만들지 않는다.
3. 질문 요약은 사용자가 눌러보기 전에도 무엇을 더 논의하는지 알 수 있을 정도로 구체적이어야 한다. 미결이 여러 개면 다음 우선순위로 1개를 고른다: `blocked-by`로 다른 질문들을 막고 있는 선행 질문 > 가장 최근 라운드에서 반복 정체된 질문 > 범위를 가장 많이 줄일 수 있는 질문.
4. 추가 논의를 선택했는데 다음 라운드도 stagnation이면, 남은 쟁점을 open question으로 기록하고 Gate 3→4로 이동한다 (Step 4 직행 금지 — 카테고리 라벨링이 필요하다).
5. 이 fallback은 토론을 강제로 닫기 위한 것이 아니라, 진전 없는 반복을 요약 가능한 상태로 전환하기 위한 것이다.

**Gate 3→4**: 기존 사용자 답변과 종료 의사를 먼저 반영한다. 미결을 해결된 결정으로 바꾸지 않는다.

1. 미결이 없으면 Step 4로 진행한다. 미결이 있으면 짧은 질문 목록을 제시한다. 사용자가 이미 그 목록을 미결로 남기고 종료하겠다고 명시했다면 추가 논의 여부를 다시 묻지 않는다. 그렇지 않으면 `AskUserQuestion`으로 "이 질문 더 논의: [질문 요약]" / "그대로 정리(미결로 기록)"를 묻는다. 추가 논의 선택은 Step 3으로 돌아간다.
2. 모든 미결에 아래 카테고리 하나를 기록한다. 기존 라벨과 명시적 사용자 분류를 유지하고, 라벨이 없거나 새 정보로 분류가 바뀐 항목만 확인한다. 미확정 항목마다 단일선택 질문으로 묻는다. 맥락상 가능한 라벨 최대 3개와 정리/종료를 제공하고 나머지는 자유 입력·후속 질문으로 받는다. 여러 라벨을 동시에 부여하지 않는다.
   - `out-of-scope` — 이 토론 범위 밖이며 별도 토론으로 분리 예정
   - `needs-data` — 외부 데이터/벤치마크/실측이 있어야 답 가능
   - `deferred-deliberately` — 의도적 보류 (후속 작업/이해관계자 대기 등)
   - `blocked-by:Q<n>` — 동일 토론 내 다른 미결 질문 번호 의존
3. 사용자가 분류를 생략하거나 정리/종료를 선택하면 맥락상 가장 가능성 높은 라벨을 추정한다. 토론 중 내부 추정한 라벨도 사용자가 확인하지 않았다면 요약에 `(auto-labeled, please review)`를 붙인다. 추정 라벨을 종료 승인으로 간주하지 않는다.
4. in-scope 미결이 남으면, 사용자가 **현재 항목과 분류를 알고 이를 남긴 채 종료하는 데 명시적으로 동의했는지** 확인한다. 이미 동의한 동일 항목은 재확인하지 않는다. 새 미결·바뀐 분류 등 아직 동의하지 않은 부분만 제시해 종료 동의를 받는다. 무응답은 승인이 아니며, 중단이면 Error Handling의 부분 저장으로 처리한다.

### Step 4: Discussion Summary (토론 정리)

**Tools**: `Read`(summary-template), `Write`

토론 종료 시 구조화된 요약을 생성하고, `_sdd/discussion/<YYYY-MM-DD>_discussion_<slug>.md`로 자동 저장한다.

- **파일명**: `<YYYY-MM-DD>_discussion_<slug>.md` 패턴. slug는 소문자 영문, 특수문자는 `_`로 대체, 최대 50자 (예: "인증 시스템 설계" → `2026-04-10_discussion_auth_system_design.md`)
- **언어**: 토론에서 사용된 언어로 작성
- **섹션 구성**: `references/summary-template.md` 코드블록을 따른다
- **조건부 포함**: "기각한 대안"은 `rejected_alternatives`가 1건 이상일 때만, "후속 핸드오프"는 실행 항목이 후속 스킬·구현으로 이어질 때만 작성한다. 해당 없으면 섹션 자체를 생략한다 — "해당 없음" 류 filler 행 금지.

#### 요약 출력 형식

요약 형식의 단일 소스는 `references/summary-template.md`다. Step 4 진입 시 이 파일을 **Read 후 코드블록을 기반으로 작성**한다. 필수 섹션과 표 구조를 유지하고 슬롯·반복 행·조건부 섹션은 템플릿 지침에 따라 실제 내용으로 채운다. 표시 언어 번역은 구조와 의미를 보존한다.

완료 시 요약 테이블을 제시한 후 전체 요약을 출력하고 파일로 저장한다 (사용자 확인을 기다리지 않는다).

## Error Handling

| 상황 | 대응 |
|------|------|
| 사용자가 토픽을 정하지 못함 | 최대 2라운드 안에 범위가 정해지지 않으면 중단·미완료. 사용자가 선택한 자유 주제도 Gate 1→2를 충족해야 진행 |
| Sub-agent 실패 | 실패 사실 보고, 토론은 수집된 맥락으로 계속 진행 |
| 사용자 응답 없음/중단 | 아래 부분 저장 규칙 적용 |
| 토론이 범위를 벗어남 | 원래 토픽 리마인드, 범위 재조정 질문 |
| 토론이 지나치게 길어짐 | §3.5.1의 stagnation fallback 적용 |
| 코드베이스 접근 불가 | Explore agent 스킵, 외부 리서치만으로 진행 |

**부분 저장:** 응답 단절·사용자 중단·도구 불가로 진행할 수 없으면 확보한 맥락이 있을 때 Step 4 형식으로 저장한다. 상태는 `중단·미완료`, 검증 결과는 미충족 AC와 이유를 기록하고, 미결·종료 동의 여부를 보존한다. 분류 근거가 없는 미결은 이 부분 저장에서만 `미확인`으로 남긴다. 저장을 위해 질문을 재개하지 않는다. 저장할 맥락이 없으면 산출물 없이 중단 사실만 보고한다.

## Integration with Other Skills

토론 결과를 후속 스킬(spec-create, feature-draft)에 활용하려면 사용자가 요약 파일을 참조하여 별도 실행한다. 후속 작업이 예정된 토론이면 요약의 "후속 핸드오프" 섹션(목표/변경 금지 제약/검증/중단 조건)이 후속 스킬의 입력 경계가 되고, 결정 테이블의 `미검증 가정` 표기는 후속 작업이 먼저 검증해야 할 전제 목록이 된다.

## Final Check

선택한 경로의 AC와 요약 구조를 검증한다. 미충족 AC가 있으면 정상 진행 중 복구 가능한 누락은 보완한다. 사용자 종료·중단이나 외부 blocker로 보완할 수 없으면 과거 라운드를 소급해 채우지 말고, 미충족 AC와 이유를 보고해 미완료로 남긴다. 부분 저장을 정상 완료나 in-scope 미결 종료 승인으로 보고하지 않는다.
