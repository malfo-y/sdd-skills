## Delivery & Review

| Component | Purpose | Why | Primary Source | Notes |
|-----------|---------|-----|----------------|-------|
| `plan-review` | 구현 전 계획을 findings-first로 감사한다 | 과잉 설계, 불필요한 새 파일, 약한 검증 기준이 구현으로 전파되기 전에 드러낸다 | `.claude/agents/plan-review-agent.md`<br>`.claude/skills/plan-review/SKILL.md`<br>`.codex/agents/plan-review-agent.toml`<br>`.codex/skills/plan-review/SKILL.md` | orchestrator(skill) + read-only leaf agent — SKILL이 동일 `plan-review-agent`를 **실측 ∥ 판단 2-렌즈**로 한 메시지 2회 병렬 dispatch하고 두 경량 반환을 병합 relay한다(Blocker Status는 하나라도 BLOCKED면 BLOCKED, findings 합산, smell 판정 합집합 — 각 smell이 정확히 한 렌즈 소유, 규모 판정 검사 결과는 판단 렌즈 반환). 렌즈 소유 정의는 agent `호출자 렌즈 한정` 절이 단일 소스다: 실측 = Step 3 계단 + `Verification Weakness` + draft 사실 주장 repo 대조(판단 렌즈 소유 smell의 사실 전제 포함), 판단 = 나머지 5 smell + 규모 판정 검사 + Step 4(Step 3 미수행·draft 내부 근거·사실 전제 UNKNOWN 금지, agent 자체 검증의 규모 판정·Step 4 항목은 판단 렌즈에만 적용). 렌즈 미지정 dispatch는 전체 6 smell 수행(후방 호환). codex SKILL은 schema-selected lifecycle과 framed payload 문법을 Codex Runtime Adapter 블록이 단일 소스로 보유한다. feature draft를 단일 패스로 리뷰하고(렌즈 2개 = 한 패스의 병렬 분해) 경량 반환으로만 응답한다(리포트 파일·re-review 없음, tools에 Write 없음). 호출 주체는 `feature-draft`다(자기 품질 게이트로 1회 호출; autopilot은 호출자가 아니다). rubric은 AC falsifiability·Target Files 실측·task boundary·6-smell·규모 판정 검사(분할 권고 포함)이며 Critical/High finding은 implementation blocker로 표시한다. 조건부 propagation 표의 발동·required surface 실측·discovery 기대 집합·단일 owner·task 연접은 기존 `Verification Weakness`가 소유하며, supporting context의 `Glob → Grep → Read` 계단에서 대조한다. finding 반영은 작성자 fix 1회, 리뷰 대상 draft가 없으면 안내 1줄만 반환한다. supporting context 읽기에는 입력 상한이 걸려 있다(렌즈 한정 시 실측 렌즈 소유) — `Glob`(Target Files와 Required surfaces의 path/pattern 존재) → `Grep`(AC content anchor와 Discovery evidence query의 기대 집합) → `Read`(Grep으로 판정이 닫히지 않는 파일 한정) → `UNKNOWN`(+limitation 1줄, 읽기 확장 금지) 계단을 밟고 상위 단계로 판정이 닫히면 내려가지 않으며, 이 읽기 규칙의 단일 소유자는 agent Step 3이다(Input 절·Error Handling 행은 포인터만). 계단과 tool call 배칭의 관계도 같은 절이 소유한다 — 배칭은 **같은 단 안에서만** 하고 다음 단을 미리 당겨 호출하지 않는다(계단은 조기 종료가 본질이라 선행 호출이 계단을 무력화한다). 이 제약은 Hard Rule에 복제하지 않아 계단 판정 주체를 한 곳으로 유지한다 |
| `implementation` | task set(주로 feature draft)을 메인 루프가 직접 RED→GREEN test-first로 구현한다 — 유일 구현 실행 경로 | 소규모 구현에서 leaf dispatch 오버헤드 없이 test-first 규율을 유지한다 | `.claude/skills/implementation/SKILL.md`<br>`.codex/skills/implementation/SKILL.md` | 작성자 불변식: 코드·테스트는 메인 루프가 직접 작성하고 read-only 보조 agent만 허용한다. 모든 실행은 resume-only implementation ledger `_sdd/implementation/<YYYY-MM-DD>_implementation_ledger_<slug>.md`를 생성·이어쓴다(같은 slug 분열 금지; 기록 기준은 재실행으로 복원할 수 없는 사실만 — 헤더 3필드 + task별 1행 6필드, 출력 전문·서술형 진행기 금지; task당 `READY → RED_CONFIRMED → GREEN_CONFIRMED → DELTA_CLOSED` 4상태에 (c) test-free는 `READY → DELTA_CLOSED` 직행; 각 단계 성공 직후 해당 task 행만 갱신; 재개 시 미완료 task는 fresh 재판정하고 DELTA_CLOSED는 diff 모순 시만 재확인; 게이트 fix는 `Review fix delta` 단일 블록; 마감 2의 AC→증거 테이블 기록처 — 채팅 노출 유지, reviewer는 ledger를 소비하지 않는다). Process는 triage → RED → GREEN → 커버리지 델타 → 테스트 불변 규칙 순이며, 커버리지 델타는 GREEN 직후 이번 task가 변경한 diff를 실행해 읽고 통과시킨 테스트가 도달하지 않는 동작을 열거·처리하는 단계다(기준점은 task 시작 시점, 커밋 경계가 없으면 이번 task가 만진 hunk 한정. (c) test-free task도 이 단계를 건너뛰지 않으며 도달 테스트/check가 0개이므로 diff 동작 전량이 열거 대상이다. 불필요분은 삭제 1순위이되 **삭제했으면 (a)/(b) task는 그 task의 테스트/check를 다시 실행해 통과를 재확인하고 출력을 갱신 캡처**한다(증거 테이블의 GREEN 증거는 삭제 이후 출력, 재확인 실패면 삭제를 되돌려 남기기 경로로 닫고, (c)는 실행할 테스트가 없어 범위 밖), 남는 항목은 triage로 닫고, 델타 테스트는 변이 확인으로 판별력 증명 + 테스트 불변 규칙 동일 적용, 마감 게이트 fix diff에도 적용, 델타 0건이면 무출력). 이 절은 적용 대상만 소유하고 `fix → 델타 → 회귀` 순서는 마감 절이 소유한다. 마감은 강제 게이트 계약이다 — 회귀 1회 → AC→증거 테이블 → `implementation-review` 1회(C/H/M fix 1회, fix가 있었으면 그 fix diff에 **커버리지 델타를 먼저 적용한 뒤** 회귀 1회 재실행 + 증거 테이블 갱신 — 델타 선행은 fix diff 한정이고 회귀는 fix 전체에 걸린다, Low advisory) → 마감 요약(게이트 finding·fix 내역·잔존 finding 포함, finding 과다 시 — fix 전 합산 기준 — `implementation-review` 1회 추가 실행 권고 1줄 advisory-only, 임계값·계약은 main.md 게이트 계약이 소유). F5에서 `implementation-lite`가 개명. 일반 구현 요청 트리거("implement the plan"·"start implementation"·"execute the plan"·"구현해줘" 계열)의 유일 수신 경로이며 "병렬 구현" 계열은 폐기됐다. 중단·분할 규칙의 canonical 소유자: 단일 세션 초과면 완료 가능한 범위까지 마감하고 잔여를 분할 feature로 draft Part 1 마커 반영 + `spec-sync` planned todo 고정, 계약 오류 선언이 같은 task에서 반복되면 구현 중단 + draft 복귀다 |
