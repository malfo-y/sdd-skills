## 결론

현재 스킬은 목적과 안전 경계를 잘 정의하지만, 질문 선택·비판 방식·종료·기록량에도 상당한 절차를 고정한다. 재설계한다면 결정의 품질과 후속 작업에 필요한 기록을 완료 기준으로 삼고, 그 기준을 달성하는 대화 방식에는 재량을 주는 방향을 권한다. 길이 자체를 줄이는 목표는 두지 않는다.

사용자는 실제 불편을 보고한 것이 아니라, 유능한 에이전트에게 어느 수준의 지시가 적합한지 검토를 요청했다. 아래 시나리오는 문면을 평가하기 위한 가상 입력이며 관측된 실패 사례가 아니다.

OpenAI 공식 문서는 GPT-6 Astra가 긴 지시를 더 잘 따르지만 불명확하거나 충돌하는 skill 지시에 민감할 수 있다고 설명한다. 이 리뷰는 “긴 지시는 모델 성능을 떨어뜨린다”는 가정을 사용하지 않는다. [공식 설명](https://developers.openai.com/api/docs/guides/latest-model#instruction-following)

## Findings

### DP-01 — 선택적 질문 가이드가 별도 실행 규칙을 소유한다 [정합성 수정 권고]

- **위치:** Codex 본문 24–25·154–162행, Claude 본문 169–178·291–292행. 양쪽 question-guide의 `Design Quality Lens`, `리서치 스킵 조건` 절(Codex 34–47·150–154행, Claude 35–48·118–121행).
- **근거:** 본문은 가이드를 질문 문형이 필요할 때 읽는 자료로 소개한다. 그러나 가이드는 설계 토픽에서 렌즈 질문을 최소 1회 수행하도록 추가 요구하고, 수렴 단계 또는 빠른 정리 요청을 리서치 생략 조건으로 둔다. 본문은 사실 확인이 필요한 주장을 조사하도록 요구한다.
- **문제 상황:** 수렴 중 결정을 바꿀 새로운 외부 사실이 등장하면, 본문은 조사를 요구하지만 가이드는 현재 페이즈를 생략 사유로 제시한다. 가이드를 읽었는지에 따라 필수 질문도 달라질 수 있다. Codex의 상위 Hard Rule이 사실 검증을 요구하더라도 하위 가이드에 반대 방향의 조건을 남길 이유는 없다.
- **권고:** 실행 조건은 본문 한 곳이 소유하고 가이드는 예시만 제공한다. 설계 렌즈를 유지하려면 판단 지침인지 필수 요구인지 본문에서 결정한다. 리서치는 새 사실의 결정 영향도와 기존 근거의 충분성으로 판단하며, 빠른 정리는 조사 범위를 줄이거나 불확실성을 기록하는 사유로 사용한다.
- **유지할 것:** 필요한 사실 확인, 근거 없는 단정 금지, 질문 예시의 선택적 로드.
- **검증:** 같은 토픽을 가이드 로드 여부만 달리해 처리했을 때 필수 검토와 사실 확인 의무가 같아야 한다. 수렴 중 새 미확인 사실은 검증하거나 미검증으로 남겨야 한다.

### DP-02 — coverage가 질문 선택의 필수 상태 기계로 사용된다 [설계 변경 후보]

- **위치:** Codex 본문 89–118행, Claude 본문 105–134행; 양쪽 가이드의 `Coverage` 예시.
- **근거:** 11개 항목을 추적하고 exploration → analysis → convergence 순서로 페이즈를 정한다. 깊이 신호가 있을 때 순서를 무시할 수 있고, 사용자 지정 방향은 alternatives 생략으로 처리하지만, 미확인 exploration/analysis를 넘기려면 별도 확인을 요구한다.
- **문제 상황:** 사용자가 배경과 제약을 이미 제공하고 하나의 불확실성만 좁히려는 토론에서도, 완료를 coverage 용어로 판단해야 한다. 이는 11번 질문을 반드시 한다는 뜻은 아니지만, 해당 토론에 적용되지 않는 항목과 실제 누락을 구별하는 일반 기준이 약하다.
- **권고:** 항목은 누락 점검용 기준으로 남기고, 다음 질문은 “답이 현재 결정·범위·다음 행동을 얼마나 바꾸는가”로 고른다. 이미 확인했거나 관련 없는 항목 때문에 질문·승인 턴을 만들지 않는다. 대안 비교도 선택이 열려 있고 구별되는 실질 대안이 있을 때 수행한다.
- **유지할 것 / 손실 위험:** 동기·제약·대안·위험을 놓치지 않는 점검은 유지한다. 페이즈를 완화하면 일찍 결론을 내리는 위험이 있으므로 중요한 누락이 늘지 않는지 비교해야 한다.
- **검증:** 맥락이 충분한 좁은 토론과 배경이 거의 없는 열린 토론을 함께 비교한다. 앞에서는 중복 질문이 없어야 하고, 뒤에서는 결정을 바꿀 제약을 실제로 발견해야 한다.

### DP-03 — 비판적 검토를 특정 질문·응답 형식으로만 인정한다 [설계 변경 후보]

- **위치:** Codex 본문 120–137행, Claude 본문 136–153행.
- **근거:** 최소 1회 비판적 질문과 사용자 응답을 요구하고, 비판은 질문 형태로 수행하도록 한다. Claude는 대안 제시 완료 또는 사용자 지정 생략 이후라는 순서도 고정한다.
- **문제 상황:** 모델이 코드를 확인해 숨은 가정이 틀렸음을 입증하고 보완책까지 제시해도, 사용자에게 별도 비판 질문을 하고 응답을 받아야 coverage가 완료된다. 분석 품질과 사용자 응답 유무가 결합되어 있다.
- **권고:** “유력한 방향의 중요한 약점·가정·반례를 검토하고 결과를 설명한다”를 필수로 둔다. 취향·우선순위·수용 가능한 손실처럼 사용자 판단이 필요한 경우에 질문한다. 직접 검증할 수 있는 사실은 조사·분석으로 충족할 수 있게 한다.
- **유지할 것 / 손실 위험:** 무비판적 동조를 막는 요구는 유지한다. 한 줄짜리 형식적 ‘검토 완료’로 약화되지 않도록 실제 주장과 근거 또는 미검증 가정이 기록됐는지 평가한다.
- **검증:** 코드로 반박 가능한 가정과 사용자 가치 판단이 필요한 트레이드오프를 각각 제시한다. 전자는 근거로 검토하고, 후자는 사용자 판단을 임의로 만들어내지 않아야 한다.

### DP-04 — 종료 판단이 추가 대화의 가치보다 미결 카테고리에 묶인다 [설계 변경 후보]

- **위치:** Codex 본문 34·179–237행, Claude 본문 27·195–253행.
- **근거:** `needs-data`는 종료 권유를 막는 in-scope 미결이다. 해당 미결이 있으면 자동으로 다음 논점으로 채택한다. 정체 fallback과 Gate에서는 종료가 가능하며, 이미 받은 종료 동의는 재사용한다. 따라서 ‘사용자가 종료할 수 없다’거나 ‘항상 재확인한다’는 판정은 아니다.
- **문제 상황:** 외부 벤치마크가 없어서 답할 수 없는 질문의 측정 방법까지 정한 뒤에도, 카테고리 때문에 일반적인 종료 권유를 할 수 없고 정체 대응 경로 등에 기대게 된다. 라벨 미확정 항목마다 분류 질문을 하는 일도 실제 의사결정과 분리되어 있다.
- **권고:** “지금 추가 대화로 해소할 수 있는가, 해소하면 다음 행동이 달라지는가”로 계속 여부를 판단한다. 외부 데이터가 필요한 미결은 필요한 근거와 다음 행동을 기록한 뒤 정리를 제안할 수 있게 한다. 라벨 확인은 오분류가 후속 처리에 영향을 줄 때로 좁히는 안을 검토한다.
- **유지할 것 / 손실 위험:** 미결을 결정으로 승격하지 않기, 사용자 종료 의사 존중, 미완료 상태 구분, 기존 동의 재사용은 유지한다. 현재 명시적 종료 동의 경계를 바꾸는 것은 정책 변경이므로 문구 축약에 섞지 않는다.
- **검증:** 데이터 대기, 아직 사용자가 선택해야 하는 중요 쟁점, 사용자의 명시적 종료를 각각 비교한다. 불필요한 반복을 줄이면서도 미결·사용자 선택·종료 상태가 사실대로 남아야 한다.

### DP-05 — 범위의 명확성을 단일 서브프로젝트로 좁히는 것과 결합한다 [설계 변경 후보]

- **위치:** Codex 본문 52–57행, Claude 본문 47–52행.
- **근거:** 독립 서브시스템 묶음은 분해한 뒤 첫 번째 서브프로젝트만 토론하도록 하고 `scope_is_atomic`을 다음 단계의 조건으로 둔다.
- **문제 상황:** “독립적인 인증·결제·알림 개선 중 이번 분기 우선순위를 결정하자”는 여러 영역을 비교하는 하나의 의사결정이다. 영역 하나를 먼저 고르면 본래 비교 목적을 잃을 수 있다. 서로 연관된 시스템을 무조건 분해한다는 주장은 아니다.
- **권고:** 범위를 “이번 토론에서 답할 질문 또는 결정”으로 정의한다. 독립 논의가 섞여 진행이 어려울 때 분해를 제안하고, 비교·공통 정책·우선순위 결정처럼 묶어서 판단해야 하는 목적은 허용한다.
- **유지할 것 / 손실 위험:** 무제한 범위 확장 방지는 유지한다. 여러 영역을 허용한 뒤 각 영역의 상세 구현까지 토론이 확장되지 않게 공동 결정의 경계를 명시한다.
- **검증:** 여러 프로젝트의 우선순위 비교와 독립적인 세 기능의 상세 설계 요청을 나란히 평가한다. 전자는 공동 결정을 유지하고 후자는 감당 가능한 논의 단위로 좁힐 수 있어야 한다.

### DP-06 — 결과 기록에 모든 라운드의 과정 기록을 기본 포함한다 [설계 변경 후보]

- **위치:** 양쪽 summary-template 53–62행; Claude 본문 270행; Codex 본문 239–255행.
- **근거:** 요약에 `토론 흐름`과 질문·선택지·답변·후속 분석의 `대화 로그`가 필수 섹션으로 들어간다. Claude는 요약 테이블 뒤에 전체 요약도 채팅으로 출력한다. 이는 템플릿 참조를 분리했어도 매번 생성하는 결과물의 크기에는 남는다.
- **문제 상황:** 결정과 이유가 짧은 토론도 라운드 단위로 다시 기록한다. 조사한 skills·tools의 명시적 참조와 feature-draft·spec-create 입력 경계에서는 이 두 섹션을 필수로 소비하는 계약을 찾지 못했다. 외부 소비자나 인간의 감사 용도가 없다는 뜻은 아니다.
- **권고:** 결정·근거·중요 맥락·미결·다음 행동을 기본 결과물로 유지하고, 전체 라운드 로그는 사용자 요청 또는 감사 필요가 있을 때 포함하는 안을 비교한다. 채팅에는 주요 결정과 문서 링크를 기본으로 보여주는 안을 검토한다.
- **유지할 것 / 손실 위험:** 초기 배경, 기각 사유, 결정 변경 이유, handoff 경계는 후속 독자가 복원하기 어려운 정보이므로 보존한다. 템플릿을 읽고 정해진 구조로 쓰는 방식 자체는 유지한다. 로그를 선택 사항으로 만들 경우 결정 경위 복원 능력이 떨어지는지 확인해야 한다.
- **검증:** 원문 대화를 모르는 후속 작성자가 요약만으로 목표·제약·결정 이유·미결을 정확히 설명하고 다음 작업을 준비할 수 있는지 비교한다. 생성량 감소만으로 성공 판정하지 않는다.

## 유지할 계약과 추가 finding으로 채택하지 않은 항목

| 계약 | 유지 이유 |
|---|---|
| 토론 중 코드·스펙·설정 수정 금지, 요약 경로와 work log 예외 | 토론의 권한과 산출 경계를 명확히 함 |
| 사실·외부 자료·사용자 판단·미검증 가정 구분 | 추론이나 선호가 검증된 사실로 승격되는 것을 막음 |
| 사용자만 정할 수 있는 선택은 묻기 | 에이전트의 능력으로 사용자 선호를 대체할 수 없음 |
| 초기 배경·결정 이유·기각 사유·중요 미결 보존 | 결론만으로 복원할 수 없는 후속 맥락 |
| 요약 템플릿 단일 소스와 작성 시 실제 로드 | 재구성에 따른 누락을 막으려는 기존 설계 근거가 있음 |
| 정상 종료와 중단·미완료 구분, Final Check | 실제 수행 범위와 결과를 과장하지 않음 |
| 런타임에 맞는 질문 도구와 실제 schema 준수 | 명시적인 대화형 UX 계약. 길다는 이유로 없애지 않음 |

결정 재방문의 횟수 제한은 검토했지만 별도 결함으로 확정하지 않았다. 실패한 결정이 open question으로 강등되어 후속 논의의 대상이 될 수 있으므로, “새 근거가 와도 영구적으로 재검토 불가”라고 단정할 근거가 부족하다. 재설계 시 새 근거와 같은 주장 반복을 구분하는 판단 기준으로 표현할 수는 있다.

## 권장 후속 작업과 검증

1. **DP-01을 먼저 정합화한다.** 질문 가이드를 예시 역할로 한정하고, 필요한 실행 조건은 본문에서 일관되게 소유한다.
2. **DP-02~06은 별도 재설계로 다룬다.** 단순 축약이 아닌 동작 변경이다. 최종 구조는 목적 / 필수 경계 / 질문·근거·종료 판단 기준 / 결과물 계약 / 관련 reference 정도면 충분하며, 특정 줄 수나 새 mode·설정 체계는 목표로 두지 않는다.
3. **같은 모델 안에서 현재 버전과 수정안을 비교한다.** 입력 시나리오와 사용자 역할의 사실·선호·응답 정책을 동일하게 두고, 실제 질문에 답하도록 한다. 질문이 달라져도 같은 답변 문자열을 억지로 재생하지 않는다. 모델 간 비교는 그 이후이며 Astra나 Fable에서 효과가 같다고 가정하지 않는다.

비교 대상은 위 finding별 시나리오다. 평가할 결과는 중요한 결정과 제약의 정확성, 미검증 가정·미결 보존, 사용자 의사 존중, 후속 인계 가능성, 불필요한 질문 수, 사용자 응답 횟수, 생성량과 소요 시간이다. 짧게 끝났어도 중요한 정보를 놓쳤다면 개선으로 보지 않는다. 이번 리뷰에서는 이 비교를 실행하지 않았다.

동작을 바꿀 때 함께 확인할 표면은 양 runtime의 본문·question-guide·summary-template, human example, [components.md의 discussion 행](../../../_sdd/spec/components.md), 관련 사용 가이드다. 과거 리뷰와 decision log는 역사적 기록으로 보존하고 새 결정만 추가한다. 현재 구현이나 spec이 제안과 다르다는 이유로 drift라고 판정하지 않는다.
